# BC02 · C10 — Environnement de test permanent

**Statut : Solide.**

## Intitulé

**Intitulé (abrégé du référentiel).** Organiser l'infrastructure pour l'intégration permanente d'évolutions logicielles.

**Critère d'évaluation.** Un environnement de tests permet la mise en production continue.

## Interprétation

Décrire précisément ce qui est contrôlé automatiquement avant mise en production, ce qui reste manuel, et le signal qui déclenche un retour arrière — sans présenter le déploiement bout en bout comme automatique tant qu'il ne l'est pas.

## Réponse

**Chaîne de test et déploiement continu du homelab.**

(1) **Détection automatisée (Renovate).** Chaque jour, Renovate scan les registres Docker (Docker Hub, Quay.io) pour les nouvelles versions d'images hébergées dans le dépôt. Quand une version mineure ou majeure est détectée, il ouvre automatiquement une PR avec les changements (`FROM image:old` -> `FROM image:new`).

(2) **Validation pré-merge (CI GitHub Actions).** Chaque PR déclenche une pipeline en lecture seule : shell-linting (`shellcheck`), validation Docker Compose (`docker compose config`), vérification Markdown, build du portfolio (Docusaurus). Aucune modification n'est deployée si la CI échoue.

(3) **Snapshot avant mise en production.** Avant de merger et déployer sur le cluster Proxmox, un snapshot LVM de tous les volumes est effectué (horodaté, libellé avec le numéro de version).

(4) **Stratégie de déploiement.** Une seule version majeure à la fois (ex. Wazuh 4.13 -> 4.14, jamais 4.13 -> 5.0 d'un coup). Après déploiement, smoke test minimal : vérifier que le conteneur redémarre et que le service est accessible (curl, connexion SSH).

(5) **Retour arrière programmé.** En cas d'échec détecté, restauration du snapshot Proxmox. Aucun déploiement entièrement automatique de la fusion à la prod : après merge, il y a toujours une étape manuelle (redémarrage du service ou commande `docker compose pull && docker compose up -d`).

**Limitations acceptées.** CV-as-Code est partiellement en place (code généré OK, mais intégration au portefeuille en cours). Le déploiement n'est pas 100 % automatisé (pas de GitOps continu type ArgoCD) mais il y a une chaîne de validation solide.

## Preuves et chemin de raisonnement

- **Fichier `renovate.json`** : configuration de Renovate (registres surveillés, stratégie d'update, labels PR).
- **Exemple de PR Renovate** : capture d'une PR ouverte par Renovate montrant le diff (ex. `docker-compose.yml` avec images à jour).
- **Historique de PR mergées** : lien vers 3-5 PR Renovate fusionnées (montrant la régularité des mises à jour).
- **Pipeline CI GitHub Actions** : capture d'une exécution réussie montrant tous les jobs (shell-lint, docker-compose, markdown, build portfolio) en vert.
- **Snapshot Proxmox horodaté** : capture de `lvscan` ou Proxmox UI montrant un snapshot nommé ex. `vol-wazuh@2026-07-28-143000`.
- **Procédure de smoke test** : écrit sous forme de checklist : (1) conteneur run. (2) logs sans erreur. (3) service accessible (curl/ping). (4) état Uptime Kuma = vert.
- **Exemple de retour arrière** : capture de l'étape de restauration (journal Proxmox, commande `lvconvert`), puis redémarrage du service.
