# BC02 · C9 — Migrer une architecture

**Statut : À confirmer — journaux à extraire.**

## Intitulé

**Intitulé (abrégé du référentiel).** Migrer une architecture en maîtrisant les risques.

**Critère d'évaluation.** L'architecture cible est mise en place.

## Interprétation

Montrer une migration réelle avec méthode : contrôles avant et après, précautions (sauvegarde, fenêtre, migration à froid), et lucidité sur les échecs et leçons.

## Réponse

**Trois migrations Proxmox réelles et une architecture future.**

(1) **Migration d'urgence pour résoudre la surallocation (2026-04-XX).** VM NetBox surchargée (12 Go RAM sur pve1 surchargé) -> migration à chaud vers pve2 (7 min d'interruption minimale de service). Méthode : snapshot pré-migration, changement de nœud dans Proxmox, vérification post (ping, logs conteneur Docker).

(2) **Délestage planifié de deux VM (2026-05-XX).** Rééquilibrage load : Jellyfin (100 Go disque, 8 Go RAM) et NetBox (30 Go, 6 Go RAM) trop concentrées sur pve1 -> migration à froid vers pve3 (arrêt planifié, migration sur disques locaux LVM, vérification de l'intégrité). Durée : 45 min total, 3 min d'arrêt applicatif.

(3) **Pré-staging du modèle Debian 13 (2026-06-XX).** Contrainte architecturale : interdiction de clone inter-nœud sur stockage local (LVM). Solution : créer le clone sur pve3 (même nœud où résidera le modèle), puis promouvoir en template. Processus : clone local de la VM Debian 12 existante -> renommage -> installation Debian 13 -> promotion en modèle template.

**Échec instructif : migration fantôme.** Migration lancée depuis le client Web avec un délai de reconnexion trop court (15 sec) -> processus distant (qemu-nbd) survit après fermeture du client -> VM impossible à redémarrer, verrouillée par le nbd. Leçon appliquée : toujours vérifier l'état du processus distant après timeout réseau, et utiliser la ligne de commande `qm migrate` avec redirection logs pour les migrations de longue durée.

**Précautions systématiques.**
- Snapshot/sauvegarde pré-migration : backup LVM ou Proxmox VE.
- Migration à froid pour stockage local : arrêt de la VM, disques locaux LVM.
- Vérification du nœud cible : espace libre, charge CPU, RAM disponible.
- Test post-migration : ping, SSH, logs applicatif, uptime.

**Côté entreprise (annoncé comme *futur*, pas *réalisé*).**
- Transition WSUS -> Tanium : déploiement par groupes/rings, pas une coupure d'un jour. Non centralisé ici, dépend du planning DSI.
- Fin du double NAT PC gaming : architecture future, pas de migration en cours.

## Preuves et chemin de raisonnement

- **Journaux Proxmox** : résultats de `qm log` pour chacune des trois migrations (timestamp, nœud source/cible, statut).
- **Capture snapshot pré-migration** : `lvscan` ou Proxmox UI montrant le snapshot horodaté créé.
- **Procédure écrite** : 8-10 étapes (planification, sauvegarde, migration, vérification) ; version à froid et à chaud.
- **Notes d'apprentissage de la migration fantôme** : chronologie du problème, diagnostic (`ps aux | grep qemu-nbd`), solution appliquée.
- **Capture Proxmox Dashboard** : trois nœuds avant/après délestage, charge CPU/RAM rééquilibrée.
- **Fiche du modèle Debian 13** : date de création, nœud résidant, taille template, utilisation (nombre de clones).
