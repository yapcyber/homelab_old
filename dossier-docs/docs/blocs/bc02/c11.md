# BC02 · C11 — Procédure d'intégration automatisée

**Statut : À confirmer — procédure à publier.**

## Intitulé

**Énoncé du référentiel.** Définir une procédure d'intégration incrémentale et automatisée des évolutions applicatives, avec validation et retour arrière explicites.

**Critère d'évaluation.** Une procédure d'intégration est définie, consultable et appliquée à une mise à jour réelle.

## Interprétation

Le critère demande une procédure **définie et consultable** : la pratique existe, elle doit être formalisée, publiée et appliquée à une mise à jour réelle.

## Réponse

**Origine de l'acquisition.** J'ai formalisé ma procédure de mise à jour de services en douze étapes reproductibles.

**Contexte.** La procédure que je suis pour mettre à jour un service suit cette séquence : (1) Identifier version cible. (2) Consulter les notes de version. (3) Rechercher les changements incompatibles. (4) Épingler la version. (5) Créer un snapshot. (6) Récupérer la configuration depuis Git (source de vérité). (7) Déployer avec Docker Compose. (8) Vérifier l'état des conteneurs. (9) Exécuter un smoke test. (10) Contrôler journaux et supervision. (11) Valider. (12) Revenir au snapshot en cas d'échec.

La rédaction distingue la **détection automatisée** (Renovate), la **validation humaine** et le **déploiement**, pas encore totalement automatique. Publication prévue sur la documentation Docusaurus.

## Preuves

- Procédure publiée en Markdown (12 étapes, pour chacune : condition d'entrée, action, condition de sortie).
- Commit de création du fichier de procédure.
- Exemple de mise à jour réelle (ex. Wazuh 4.13 → 4.14).
- Capture PR Renovate (diff du docker-compose.yml).
- Sortie `docker compose pull && up` (pull OK, démarrage).
- Résultat smoke test (curl, logs sans erreur).
- Graphique Grafana : CPU/RAM stables post-déploiement.
- Test de restauration : logs du revert et redémarrage.
