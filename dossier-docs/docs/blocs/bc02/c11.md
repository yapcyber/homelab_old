# BC02 · C11 — Procédure d'intégration automatisée

**Statut : À confirmer — procédure à publier.**

## Intitulé

**Intitulé (abrégé du référentiel).** Définir une procédure d'intégration incrémentale et automatisée des évolutions applicatives.

**Critère d'évaluation.** Une procédure d'intégration est définie.

## Interprétation

Le critère demande une procédure **définie et consultable** : la pratique existe, elle doit être formalisée, publiée et appliquée à une mise à jour réelle.

## Réponse

**Procédure d'intégration incrémentale : 12 étapes de mise à jour d'un service.**

Prérequis : code versionné en Git (source de vérité), déploiement via Docker Compose, configuration en .env ou fichiers YAML.

1. **Détection (Renovate)** : Renovate détecte la nouvelle version, ouvre une PR.
2. **Audit des changements** : consultation des release notes et changelog pour identifier les breaking changes.
3. **Évaluation de compatibilité** : vérifier les dépendances (ex. Wazuh 4.14 exige PostgreSQL ≥ 12).
4. **Pinning de la version** : mise à jour `docker-compose.yml` avec la version cible (ex. `image: wazuh/wazuh:4.14.0`).
5. **Snapshot pré-patch** : création d'un snapshot Proxmox LVM (horodaté, libellé `wazuh-4.13-safe`).
6. **Git pull** : récupération de la configuration depuis le dépôt (garantit cohérence locale/distante).
7. **Déploiement** : `docker compose pull && docker compose up -d` sur la cible.
8. **Vérification conteneur** : `docker ps` et `docker compose logs` (pas d'erreur, containeur en *up*).
9. **Smoke test** : test applicatif minimal (ex. Wazuh : accès Web UI, API status 200).
10. **Supervision** : vérification Uptime Kuma + Grafana (aucune alerte non attendue).
11. **Validation** : si tout est stable > 10 min, acceptation implicite. Sinon -> 12.
12. **Retour arrière (si échec)** : `lvconvert --merge /dev/pve/vm-xxx@snapshot` -> redémarrage conteneur sur version ancienne.

**Statut d'automatisation.** La détection (étape 1) est 100 % automatique. Les étapes 2-6 et 8-12 sont manuelles (exigent un décideur humain). Une chaîne GitOps (ArgoCD) pourrait automatiser 7 et 8, mais ce n'est pas en place. C'est décrit sans artifice.

**Publication.** Cette procédure est à rédiger en Markdown et versionnée dans `docs.yapserver.fr/procedures/` ou GitHub Wiki.

## Preuves et chemin de raisonnement

- **Procédure écrite** : document Markdown avec les 12 étapes, et pour chacune : condition d'entrée, action, condition de sortie, alternatives.
- **Commit de création** : historique Git montrant l'ajout du fichier de procédure (date, auteur).
- **Exemple mise à jour réelle** (ex. Wazuh 4.13 -> 4.14) :
  - Capture de la PR Renovate (avant/après).
  - Capture snapshot créé (`lvscan` montrant `vm-xxx@2026-07-28-143000`).
  - Sortie `docker compose pull && up` montrant le pull OK et démarrage du service.
  - Résultat smoke test : `curl http://localhost:9200/_cluster/health` -> `status: green`.
  - Graphique Grafana : CPU/RAM stables pendant les 10 min post-déploiement.
  - Logs `docker compose logs wazuh-manager | tail` : aucune erreur, service opérationnel.
